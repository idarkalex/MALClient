KEY FINDINGS
------------
* NO Xamarin.Forms is in use. The project is a native Xamarin.Android app
  using Fragment-based UI with MvvmLight + MVVM. Therefore:
    - 0 classes extend ViewRenderer<,> (Xamarin.Forms renderer pattern)
    - 0 classes extend Renderer (Xamarin.Forms Android renderer base)
    - 0 references to FFImageLoading.Forms.*
    - 0 references to CachedImage (the XF wrapper from FFImageLoading)
* FFImageLoading IS used, but only the platform-side packages:
    - Xamarin.FFImageLoading  (ImageService, ImageViewAsync)
    - Xamarin.FFImageLoading.Transformations (CircleTransformation, BlurredTransformation)
* 0 AXML/XAML uses FFImageLoading namespace (it's all done in C# code-behind).
* Only 1 csproj has the packages: MALClient.Android.csproj.

MIGRATION IMPLICATIONS (Xamarin.Android -> .NET MAUI)
-----------------------------------------------------

1. There are NO Xamarin.Forms renderers to port. The migration of UI is a
   complete rewrite to MAUI's Handler architecture -- there is no shared
   "port the renderer" path.

2. The largest concrete migration surface is FFImageLoading itself.
   - FFImageLoading for Xamarin.Android is unmaintained since ~2022.
   - MAUI-side the recommended replacement is CommunityToolkit.Maui
     (MauiHandlers + ImageSource) or Microsoft.Maui.Graphics.
   - All `ImageViewAsync` view references in the 55 IMAGE_LOADING files
     have to be replaced with the new image source.
   - All `ImageService.Instance.LoadUrl(...).Into(imageAsync)` calls have
     to be replaced with `image.SetImageSource(new UriImageSource { Uri = ... })`
     or a similar wrapper.
   - `AnimeImageExtensions.AnimeInto(...)` (AnimeInto, AnimeIntoIfLoaded,
     GetImgUrl) is the central helper used everywhere -- replacing its
     internals lets us touch 1 file and rewire every consumer.
   - Custom transformations:
        - `CircleTransformation` -> MauiBorder rounded corners or a
          custom IImageSourceHandler that draws into a circular bitmap.
        - `BlurredTransformation` -> PlatformEffect / handler with
          BlurView or a Blur ImageSharp pipeline.

3. Custom Android views (ZoomableImageView, FavouriteButton, BBCodeEditor,
   UserControlBase) need MAUI Handlers. For most, a Grid with BindableProperty
   wrapping the existing Android widget via a handler will be the cleanest
   port. For FavouriteButton/BBCodeEditor a ContentView with an inner
   GridLayout is straightforward. ZoomableImageView is the trickiest:
   MAUI's built-in gestures do not give pixel-perfect pinch-zoom on raw
   bitmaps, so plan for a GraphicsView or SkiaSharp port.

4. PagerSlidingTabStrip.OnDraw (the only OnDraw override outside of the
   FFImageLoading pipeline) -- in MAUI, replace with either a custom
   Microsoft.Maui.Graphics IDrawable on a GraphicsView, or with a Border
   + shadow / SkiaSharp. The behavior is "draw underline + tab divider
   lines based on scroll position". Re-implementing on SkiaSharp is the
   modern path.

5. WebView clients (InlineVideoWebViewClient, ListenableWebClient) have
   no exact MAUI equivalent. Plan for:
        - ListenableWebClient -> MAUI WebViewHandler overrides
          (IPlatformWebViewClient.OnPageStarted/Finished + HandlerChanged
          events for navigation intercept).
        - InlineVideoWebViewClient -> same approach with custom url
          rewriting on ShouldInterceptRequest.
        - DataJavascriptInterface -> bridge a JS object via EvaluateJavaScriptAsync
          and a C# event sink; in MAUI this maps to a hybrid WebView
          handler that calls CoreWebView2.AddScriptToExecuteOnDocumentCreated
          (Windows) or WebKit's WKUserContentController (iOS/MacCatalyst).

6. ListView/GridView/ViewPager measurement overrides -- MAUI's CollectionView
   and CarouselView handle wrapping content for free; the custom HeightAdjustingListView
   and ExpandableGridView can be deleted and replaced with CollectionView.
   HeightAdjustingViewPager maps to CarouselView (or TabView with IndicatorView).
   PriorityListView / PriorityScrollView performance hacks are no longer
   needed -- MAUI's virtualization is good.

7. The pull-to-refresh wrapper (`ScrollableSwipeToRefreshLayout`) is
   already a thin SwipeRefreshLayout subclass; replace with MAUI RefreshView.

8. FlingCollectionsHelper (AbsListView + LiveFlingAdapter) is the most
   project-specific chunk of code: it pre-creates ViewHolders during
   fling to keep scrolling smooth. In MAUI this pattern is built into
   CollectionView's DataTemplateSelector + recycling pool; the helper
   itself can be deleted.

9. The bindings project PagerSlidingTabStrip (under AndroidBindings/) is
   the upstream copy; UserControls/PagerSlidingTabStrip.cs is the local
   fork. Both must be ported (or both can be deleted once MAUI's TabView
   is wired in).

10. NuGet packages to drop from csproj:
        - Xamarin.FFImageLoading
        - Xamarin.FFImageLoading.Transformations
    and add:
        - Microsoft.Maui.Controls (transitively)
        - CommunityToolkit.Maui (or CommunityToolkit.Maui.Markup + an
          image-loader of choice)
        - SkiaSharp.Views.Maui.Controls  (if SkiaSharp is needed for the
          PagerSlidingTabStrip port)
